# 双龙装饰·Agent 候选事项与模块化经营数据平台设计

## 1. 文档状态

- 设计日期：2026-08-03
- 业务确认人：老板
- 当前阶段：Phase 1B 核心业务闭环设计
- 主要模型：小米 MiMo OpenAI-compatible API
- 主要文本模型：`mimo-v2.5-pro`
- 主要语音识别模型：`mimo-v2.5-asr`
- 运行形态：单体模块化应用，不采用微服务

## 3. 设计目标

1. 同时处理文字、语音、图片和文件，不遗漏文字直通链路。
2. Agent 将聊天拆成可独立确认的原子业务事实。
3. 多条聊天中的同一事项合并成一条候选，但保留全部来源。
4. 所有 Agent 候选事项由老板逐条确认，不批量写入正式业务表。
5. 老板可直接确认、修改后确认、驳回、指派负责人后确认。
6. 未确认事项在 AI 待确认中心和对应业务模块同时可见，但不进入正式统计。
7. 管理后台、API、数据库表和测试都按业务模块分离，便于后续维护。
8. 不破坏现有企业微信采集服务和 `public` 中的生产表。

## 4. 非目标

- 本阶段不将系统拆分为微服务。
- 不把 PostgreSQL 开放到公网。
- 不让浏览器直接连接 PostgreSQL。
- 不让 Agent 直接覆盖正式业务数据。
- 不要求员工的所有手工操作均由老板逐条确认。
- 不引入 Coze 作为生产运行依赖。
- 不强制替换小米 MiMo API。

## 5. 已确认的业务规则

### 5.1 确认粒度

- 每条 Agent 候选事项必须由老板逐条确认。
- 同一条聊天同时包含到货、付款和排班时，拆成 3 条原子候选。
- 3 条候选可共享同一条消息证据，但分别确认。

### 5.2 去重和冲突

- 多条消息重复描述同一事项时，合并为一条候选事项。
- 合并后的候选关联所有文字、语音转写、图片或文件证据。
- 候选与已有正式数据重复或冲突时，不自动覆盖。
- 老板可选择更新原记录、保留原记录并新建、合并信息或驳回。

### 5.3 员工手工操作

- 只有 Agent 提取的候选事项必须老板逐条确认。
- 员工手工录入和修改按角色权限与业务审批规则处理。
- 财务、报价、设计变更、增减项和永久删除仍由老板终审。

## 6. 总体架构

```text
企业微信会话存档
        ↓
原始消息和媒体索引
        ↓
按类型分流
├─ 文字 → 文字标准化
├─ 语音 → 下载 → MiMo ASR 转写 → 文字标准化
├─ 图片 → OCR/人工补录 → 文字标准化
└─ 文件 → 文件解析/人工补录 → 文字标准化
        ↓
MiMo Agent 原子事实拆分
        ↓
候选事项 + 来源证据 + 去重 + 冲突
        ↓
老板逐条确认/修改/驳回/指派
        ↓
模块投影器
        ↓
工地/采购/客户/财务/报价/库存/排班/售后正式表
```

### 6.1 核心实现形态

- 使用一个 PostgreSQL 实例。
- 使用多个 PostgreSQL Schema 进行逻辑隔离。
- 使用一个 Fastify API 进程，内部按模块拆分。
- 使用 systemd service/timer 运行语音、Agent、投影和重试任务。
- 不额外引入 Redis、Kafka 或 RabbitMQ。
- 数据库任务表同时承担轻量任务队列和幂等状态管理。

## 7. PostgreSQL Schema 和核心表

### 7.1 `ingestion`：原始输入

- `messages`：第一阶段为指向 `public.messages` 的只读兼容视图，统一暴露消息索引、类型、时间和来源标识。
- `media`：第一阶段为指向现有媒体表的只读兼容视图，统一暴露媒体类型、校验值、下载和转写状态。
- `transcripts`：语音转写、模型、语言、时长、置信信息和转写时间。
- `normalized_texts`：文字、语音转写、OCR 或文件解析形成的统一 Agent 输入。
- `processing_failures`：采集、下载、转写、OCR 和解析失败。

初期不迁移、复制或双写现有 `public.messages` 和媒体表。兼容视图/适配层从旧表只读消费，新的标准化、候选和处理状态写入新 Schema。只有在独立迁移计划通过备份恢复演练后，才能将兼容视图替换为新的权威表。

### 7.2 `agent`：候选事实

- `runs`：模型、版本、提示词版本、输入数量、耗时、状态和费用元数据。
- `candidates`：原子候选事项、目标模块、业务类型、结构化负载、置信度和审核状态。
- `candidate_sources`：候选与原始文字、语音转写、图片或文件的多对多关系。
- `candidate_duplicates`：疑似重复、合并目标、相似分数和判断来源。
- `candidate_conflicts`：与正式记录的冲突字段和可选处理。
- `processing_failures`：模型连接、超时、格式校验、去重和冲突检查失败。

### 7.3 `review`：老板确认

- `decisions`：确认、修改后确认、驳回、冲突处理和操作人。
- `candidate_edits`：Agent 原始负载、老板修改后负载和字段差异。
- `assignments`：老板指派的人员、团队、期限和说明。
- `reminders`：超时待确认提醒。
- `projection_jobs`：已确认候选写入正式模块的幂等任务。

### 7.4 正式业务 Schema

- `projects`：项目、阶段、进度、风险和现场记录。
- `procurement`：材料需求、采购单、付款、发货、到货和验收。
- `crm`：客户、意向、跟进、成交和流失。
- `finance`：应收、应付、收入、支出和资金账户。
- `quotations`：设计图、报价、版本、增减项和审批。
- `inventory`：入库、领料、退料、损耗、调拨和盘点。
- `scheduling`：固定员工、临时工、外包个人/班组和排班。
- `aftersales`：建议、投诉、维修、回访和关闭。
- `audit.entries`：操作人、时间、对象、变更前后值、原因和来源。

## 8. 候选状态机

```text
pending_review
├─ confirmed → projection_pending → projected
├─ edited_and_confirmed → projection_pending → projected
├─ assigned_and_confirmed → projection_pending → projected
├─ conflict_review → confirmed/rejected
└─ rejected
```

投影失败时进入 `projection_failed`，重试时复用同一幂等键。老板不需要重复确认。

## 9. 模块投影规则

- 每条候选只有一个主要目标模块。
- 一条原始消息可生成多条不同模块的候选。
- 每个模块实现独立 projector，仅有权写自己的 Schema。
- projector 校验候选状态、负载版本、必填字段和幂等键。
- 工地、采购和 CRM 是第一批正式投影模块。
- 财务、报价、库存、排班和售后在基础闭环稳定后分批实现。

## 10. 应用模块与 API

Fastify 应用保持单进程，内部按模块分离：

```text
modules/<module>/
├─ route
├─ service
├─ repository
├─ projector
├─ contract
└─ tests
```

API 前缀：

- `/api/review/*`：AI 待确认、确认、修改、驳回、指派和冲突处理。
- `/api/projects/*`：工地管理。
- `/api/procurement/*`：主材采购。
- `/api/crm/*`：客户销售。
- `/api/finance/*`：财务中心。
- `/api/quotations/*`：设计报价。
- `/api/inventory/*`：库存管理。
- `/api/scheduling/*`：员工排班。
- `/api/aftersales/*`：售后管理。
- `/api/evidence/*`：文字、语音转写、图片和文件来源。
- `/api/audit/*`：审计记录。

`/api/review/*` 只提供单候选确认命令，命令必须携带候选 ID、当前版本和幂等键。后端不提供“全部确认”或批量确认接口，防止绕过老板逐条处理规则。

不为每个模块开放新的公网端口。Nginx 仅对外提供 HTTPS，API 仍仅监听 `127.0.0.1:3001`。

## 11. 管理后台交互

### 11.1 AI 待确认中心

每条候选显示：

- 候选类型和目标模块。
- Agent 结构化结果和置信度。
- 疑似重复和冲突。
- 文字、语音转写、图片或文件来源数量。
- 建议负责人。
- 生成时间和等待时长。

老板可以：

- 确认。
- 修改字段后确认。
- 驳回并填写原因。
- 指派负责人和期限后确认。
- 处理重复和冲突。
- 展开来源证据。

### 11.2 业务模块中的未确认数据

- 未确认候选在相应模块可见。
- 统一显示“待老板确认”。
- 不进入正式金额、工地进度、库存、销售漏斗或老板行动统计。
- 员工不能将其当作正式任务处理。
- 点击后进入 AI 待确认中心的对应事项。
- 投影成功后，候选卡片替换为正式业务记录。

## 12. 权限设计

- 企业微信采集服务：仅写原始采集范围。
- 语音处理器：仅读媒体任务，写下载/转写状态。
- Agent 处理器：读标准化文字，仅写 `agent`。
- 老板审核服务：写 `review`，不直接修改业务表。
- 模块 projector：只能写指定业务 Schema。
- 管理后台 API：使用专用账号，按登录角色执行。
- 浏览器：只通过 HTTPS API 访问，永不持有数据库连接串。

真实数据进入公网管理后台前，必须完成登录、服务器会话、RBAC、敏感操作再验证和审计。

## 13. 小米 MiMo 模型适配

### 13.1 默认配置

- 业务事实提取：`mimo-v2.5-pro`。
- 语音识别：`mimo-v2.5-asr`。
- 协议：OpenAI-compatible API。
- 密钥：仅放在服务器权限受控环境文件中，不进入 Git、日志或数据库业务表。

### 13.2 适配器边界

```text
TextModelProvider
├─ MiMoProvider
└─ LocalRuleFallback

SpeechRecognitionProvider
└─ MiMoAsrProvider
```

业务模块不引用 MiMo 具体请求格式。将来替换模型时，只新增 provider 适配器。

### 13.3 费用和失败控制

- 语音单条串行处理，并发度默认为 1。
- 文本 Agent 使用有限批次，不将全部历史聊天重复发给模型。
- 保存模型、耗时、成功/失败、可用 token/费用元数据，但不保存密钥。
- 超时、429、5xx 使用有上限的指数退避。
- 格式校验失败不写入候选表，进入人工处理或有限重试。
- 达到日费用或调用上限时停止新调用并通知老板。

## 14. 后台任务和幂等

使用轻量 systemd service/timer：

- `voice-sync`：补齐语音 media、下载、转写和标准化文字。
- `agent-candidate`：扫描尚未分析的标准化文字，生成原子候选。
- `candidate-dedup`：去重、合并证据和冲突标记。
- `review-reminder`：通知老板超时待确认。
- `module-projector`：投影已确认候选。
- `retry-worker`：有界重试和失败告警。

每个任务都必须有幂等键、锁定超时、尝试次数和最终失败状态。服务器重启后可以续跑，不重复生成正式记录。

## 15. 错误处理

统一处理状态：

```text
pending → processing → completed
                    └─ retryable → processing
                    └─ failed_permanent
                    └─ manual_review
```

- 一条语音失败不影响文字和其他语音。
- 转写失败时保留媒体索引、校验值和脱敏错误类型。
- 模型失败不得生成部分正式候选。
- 投影失败保留已确认决策，不要求老板重复确认。
- 日志不记录完整聊天、转写文本、客户姓名、密钥或数据库连接串。

## 16. 迁移与上线顺序

### 16.1 第一步：修复断链

1. 为现有 `voice:sync` 建立受控调度。
2. 补处理最新未转写语音。
3. 将文字原文和语音转写同时进入统一标准化文字层。
4. 让语音转写生成带来源关联的 Agent 候选。

### 16.2 第二步：核心 Schema

1. 备份应用、数据库 Schema 和 Nginx/systemd 配置。
2. 创建 `ingestion`、`agent`、`review`、`audit`。
3. 创建最小权限数据库角色。
4. 通过兼容层只读消费旧 `public` 表。

### 16.3 第三步：老板确认闭环

1. 候选事项、证据、去重和冲突。
2. 确认、修改确认、驳回和指派确认。
3. 投影任务和审计记录。

### 16.4 第四步：首批正式模块

1. `projects`：工地进度和风险。
2. `procurement`：主材需求、付款、发货、到货和验收。
3. `crm`：意向客户和跟进。

### 16.5 第五步：真实管理后台

1. 完成登录、服务器会话、RBAC 和审计。
2. 管理 API 改用专用权限账号。
3. 从 demo/mock 切换为真实模块数据。
4. 小范围真实数据试运行后再扩大范围。

## 17. 测试策略

### 17.1 功能测试

- 文字消息直接进入标准化和 Agent。
- 语音消息经转写后进入同一 Agent 管道。
- 一条聊天拆分成多个原子候选。
- 多条聊天合并为同一候选并保留多来源。
- 冲突候选不覆盖正式数据。
- 老板确认、修改确认、驳回和指派确认。
- 未确认候选不进入正式统计。
- 已确认候选写入正确模块。

### 17.2 可靠性测试

- 重复采集、重复转写、重复 Agent 运行和重复投影不产生重复正式数据。
- 语音失败、模型超时、格式错误、数据库短暂不可用可以恢复。
- 投影失败不丢失老板确认结果。
- 服务器重启后自动继续未完成任务。
- 备份可实际恢复。

### 17.3 安全测试

- 未登录不能查看真实数据。
- 非老板不能处理 Agent 候选。
- 角色不能越权读写其他模块。
- Agent 数据库角色不能写正式业务表。
- 浏览器 bundle、Git、日志和 API 错误不含密钥、完整聊天或数据库连接串。

## 18. 上线验收条件

- 新文字和新语音都能自动进入候选链路。
- 语音转写候选可反查原始语音索引和转写记录。
- 所有 Agent 候选都是逐条老板确认。
- 未确认候选在业务模块可见，但不进入正式统计。
- 重复和冲突有明确的老板选择界面。
- 老板修改前后值、指派和驳回原因可审计。
- 首批工地、采购和 CRM projector 具有幂等测试。
- 真实数据切换前，登录、RBAC、审计和专用数据库权限全部验收。
- 不影响现有企业微信采集服务，PostgreSQL 继续仅监听本机。

## 19. 实施拆分

本设计不在一个发布中一次完成。实施计划必须拆为以下可独立验收子项目：

1. **1B-1 输入与 Agent 基础**：文字/语音统一标准化、自动调度、候选、证据、去重和冲突。
2. **1B-2 老板确认闭环**：登录基础、待确认中心、确认/修改/驳回/指派、审计和投影任务。
3. **1B-3 首批业务模块**：工地、主材采购和意向客户。
4. **1C 生产安全与真实数据切换**：完整 RBAC、数据库最小权限、监控、备份恢复和小范围上线。
